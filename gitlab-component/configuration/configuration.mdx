This page lists every input and output of `gitlab.com/ironbee-ai/ironbee-gitlab/verify@v1`. The **Mode** column shows where an input applies:
- **Both** means both modes.
- **Platform** means on IronBee.
- **Local** means on your runner.

The component logs a warning when you set an input that doesn't apply to the mode it runs in. See [Platform and local verification](/gitlab-component/concepts/verification-modes).

Only `ironbee_api_key` is required, and it reads the `IRONBEE_API_KEY` CI/CD variable by default. Every run also needs a target: `app_url`, or `app_start_command` with `app_port`. See [Verifying your application](/gitlab-component/guides/verifying-your-app).

---

## Input values

- Every input is a string, numbers and `true`/`false` included, so quote them: `app_port: '3000'`. GitLab refuses an input whose value isn't a string.
- Any input except `stage` and `job_name` can be a `$VARIABLE`, which GitLab expands when the job starts. A literal `$` is written `$$`.
- The five commands (`app_install_command`, `app_build_command`, `app_start_command`, `app_restart_command`, `app_logs_command`) and `claude_code_args` are the exception: GitLab leaves them as written, and bash expands them when they run. A `$MY_COMMAND` there expands into words; a command holding `&&`, a pipe or quotes needs `eval "$MY_COMMAND"`.
- Every `true`/`false` input also accepts `1`/`0`, `yes`/`no` and `on`/`off`. Any other value fails the run and names the input.

## IronBee account and endpoints

| Input | Default | Mode | Description |
|-------|---------|------|-------------|
| `ironbee_api_key` | `$IRONBEE_API_KEY` | Both | Your IronBee account API key, from **Settings > Account** in the console. Store it as a masked CI/CD variable |
| `ironbee_cli_version` | `latest` | Both | IronBee CLI version to install, such as `0.52.0`. Empty means `latest` |
| `ironbee_project` | Empty | Platform | The project the run reports to. Empty derives it from the git remote |
| `ironbee_environment` | Empty | Platform | The project environment the run is against, by name. Selects that environment's variables and secrets on top of the project-wide ones. A new name is created by the first run that uses it. Empty falls back to the job's own `environment:` (`CI_ENVIRONMENT_NAME`) |
| `ironbee_api_url` | Empty | Platform | IronBee API base URL. Leave empty |
| `ironbee_collector_url` | Empty | Both | IronBee collector URL. Leave empty. On IronBee, your app's commands get the resolved URL as `IRONBEE_COLLECTOR_URL`, with the key as `IRONBEE_API_KEY`. See [Your app's own telemetry](#your-apps-own-telemetry) |
| `ironbee_console_url` | Empty | Both | Console hostname, without a scheme, used for links in the report. Empty derives it from the collector URL |

## What to verify and what to do about it

| Input | Default | Mode | Description |
|-------|---------|------|-------------|
| `verification_prompt` | Empty | Both | Additional instructions for the verification |
| `verification_auto` | `'true'` | Both | Set `'false'` to verify only in a manual pipeline. Every other pipeline, schedules included, then does nothing. See [Turning automatic verification off](/gitlab-component/guides/running-in-ci#turning-automatic-verification-off) |
| `verification_apply_fix` | `'true'` | Platform | Fix the issues a failing verification on IronBee reports, on your runner. Needs an Anthropic credential; without one the run verifies and reports only. On your runner, the agent always fixes what it finds, whatever this input says |

The component has no `verification_command` input: GitLab CI/CD has no pipeline trigger for a merge request note.

## The job itself

The component adds one job. These inputs place it:

| Input | Default | Description |
|-------|---------|-------------|
| `stage` | `test` | The stage the job runs in |
| `job_name` | `ironbee-verify` | The job's name, and the name you redeclare to extend it |
| `image` | `node:22-bookworm` | The image the job runs in. It needs Node 22, bash, git, curl and apt-get |

Anything else, such as a `timeout:`, `services:`, `environment:`, `tags:` or `rules:`, goes on a job of the same name in your own `.gitlab-ci.yml`. GitLab merges it into the component's job:

```yaml
ironbee-verify:
  timeout: 2h
  # Becomes ironbee_environment when that input is empty.
  # `action: verify` keeps each run from being recorded as a deployment.
  environment: { name: staging, action: verify }
  tags: [docker]
  services:
    - postgres:16
```

### Your app's own telemetry

When the component starts your app for a run on IronBee, your app's install, build, start and restart commands run with `IRONBEE_COLLECTOR_URL` (the collector the run reports to) and `IRONBEE_API_KEY` in their environment. An app whose OpenTelemetry exporter reads them ships its traces and logs into the verification run, next to the rest of its evidence. Nothing is written to disk for it.

### Credentials in the job

GitLab puts every CI/CD variable in the environment of everything a job starts. The component takes its own inputs back out of the environment, together with `IRONBEE_API_KEY`, `ANTHROPIC_API_KEY`, `CLAUDE_CODE_OAUTH_TOKEN` and `GITLAB_TOKEN`, and gives each step only what it needs. A credential you keep under another variable name is still visible to every process in the job, your app included.

## Outputs

The job writes its outputs as a dotenv report. A later job that `needs: [ironbee-verify]`, or any job in a later stage, reads them as variables:

| Variable | Description |
|----------|-------------|
| `IRONBEE_VERDICT` | `pass`, `fail`, `not_applicable` or `unknown` |
| `IRONBEE_MODE` | Where the verification ran: `platform` or `local` |
| `IRONBEE_JOB_ID` | The verification run's id. Platform mode only; after a fix, the re-verification's id |
| `IRONBEE_JOB_URL` | Link to the run in the IronBee Console. Platform mode only, once the run has started |
| `IRONBEE_ARTIFACTS_URL` | Where to browse the job's evidence artifacts. Local mode only; evidence from a run on IronBee is in the console |
| `IRONBEE_PLATFORM_PUBLISHES` | `true` when IronBee publishes the run on the repository itself: the status on the commit, and on a merge request its comments and summary note. The component then posts no report note. `false` otherwise, and always in local mode |

```yaml
report-verdict:
  stage: deploy
  when: always
  needs:
    - job: ironbee-verify
      optional: true
  script:
    - echo "Verdict $IRONBEE_VERDICT, run $IRONBEE_JOB_URL"
```

`when: always` runs it when the verification fails too, and `optional: true` keeps the pipeline valid where the component's job doesn't run, such as a push to a feature branch.

## Caching

In local mode, the Playwright Chromium binaries are cached with the job's `cache:` to speed up later runs. GitLab caches only paths inside the project directory, so they live in `.cache/ms-playwright` there, and the component tells git to ignore that folder. Platform mode installs no browser.
