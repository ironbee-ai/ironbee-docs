The IronBee GitLab component can run the verification in two places:

- **Platform mode:** on IronBee. The console calls this **On IronBee**.
- **Local mode:** on your GitLab runner. The console calls this **On your GitLab runner**.

Everything after the verification works the same way in both modes: the verdict, the fix, the commit and the report. Only a run on IronBee can be [published on the merge request](/gitlab-component/guides/running-in-ci#the-report) by IronBee itself. The `verification_mode` input picks the mode: `auto` (the default), `platform` or `local`.

---

## Compare the two modes

| | Platform (on IronBee) | Local (on your runner) |
|---|---|---|
| Where the agent runs | IronBee's infrastructure | Your GitLab runner |
| Model access | IronBee's | Your Anthropic API key or Claude Code OAuth token |
| Runner setup | None: no Chromium, no DevTools install | Chromium, IronBee DevTools and Claude Code, installed on every run |
| Anthropic credential | Only to fix what it finds | Required |
| What it verifies | Your web app, in a browser | The [DevTools platforms](/gitlab-component/guides/verification-platforms) you enable: browser, backend, Node.js, Python, terminal |
| Evidence | The IronBee Console | The IronBee Console and the job's artifacts |
| Private projects | Need the project's group [connected to IronBee](/integrations/gitlab) | Work with any checkout |

---

## How `auto` decides

With `verification_mode: auto`, the component decides from two things it can check without calling IronBee: the project's visibility, and whether an Anthropic credential is set.

| Project visibility | Anthropic credential | Mode |
|--------------------|----------------------|------|
| Public | Any | Platform. IronBee can check out a public project without the GitLab connection |
| Private or internal | Set | Local. The component can't check whether the GitLab connection covers the project, so it uses the engine it knows can run |
| Private or internal | Not set | Platform, the only engine available. This needs the project's group connected to IronBee |

The first line of the plan in the job log names the mode and the reason.

<Tip>
  If your project is private or internal and its group is [connected to IronBee](/integrations/gitlab), set `verification_mode: platform` explicitly. Otherwise `auto` runs on your runner whenever an Anthropic credential is set.
</Tip>

A private project whose group isn't connected can still be verified on IronBee: set `ironbee_bind_repository: 'false'` to verify the running application without a checkout of the repository.

## Inputs that apply to one mode

The component warns in the job log when you set an input that doesn't apply to the mode it runs in.

**Platform mode only**

| Input | Purpose |
|-------|---------|
| `ironbee_project` | The project the run reports to. Empty derives it from the git remote |
| `ironbee_environment` | The project environment whose variables and secrets the run uses |
| `ironbee_bind_repository` | Bind the run to the repository so it verifies the changeset |
| `ironbee_job_timeout_minutes` | The run's timeout on IronBee |
| `app_restart_command`, `app_logs_command`, `app_wait_seconds` | An app that runs on the runner, reached through a tunnel |
| `app_headers`, `app_secret_headers` | Request headers for a deployed URL |

**Local mode only**

| Input | Purpose |
|-------|---------|
| `ironbee_browser_devtools`, `ironbee_backend_devtools`, `ironbee_node_devtools`, `ironbee_python_devtools`, `ironbee_terminal_devtools` | The DevTools platforms the agent verifies through |
| `ironbee_extra_config` | Raw IronBee CLI config. See [Custom configuration](/gitlab-component/advanced/custom-configuration) |
| `claude_code_model`, `claude_code_max_turns`, `claude_code_args` | The Claude Code agent on your runner |

`claude_code_cli_version` and the Anthropic credential also apply to the fix step in platform mode. See [Configuration](/gitlab-component/configuration/configuration) for every input.
