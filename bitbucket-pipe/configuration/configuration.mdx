This page lists every variable and output of `docker://ghcr.io/ironbee-ai/ironbee-bitbucket:v1`. The **Mode** column shows where a variable applies:
- **Both** means both modes.
- **Platform** means on IronBee.
- **Local** means on your runner.

The pipe logs a warning when you set a variable that doesn't apply to the mode it runs in. See [Platform and local verification](/bitbucket-pipe/concepts/verification-modes).

Only `IRONBEE_API_KEY` is required. Every run also needs a target: `APP_URL`, or `APP_START_COMMAND` with `APP_PORT`. See [Verifying your application](/bitbucket-pipe/guides/verifying-your-app).

---

## Variable values

- A pipe sees a repository variable only when the step passes it, so pass every credential under `variables:`, as in `IRONBEE_API_KEY: $IRONBEE_API_KEY`.
- Bitbucket expands each `$NAME` when it starts the pipe. A command that needs a variable expanded when it runs is better kept in a script file that the command calls.
- Bitbucket doesn't type-check a pipe's variables, so quote numbers and `true`/`false`: `APP_PORT: "3000"`.
- Every `true`/`false` variable also accepts `1`/`0`, `yes`/`no` and `on`/`off`. Any other value fails the run and names the variable.
- A variable passed empty is empty, not its default. An empty `true`/`false` variable, `VERIFICATION_MODE`, `WORKING_DIRECTORY`, `IRONBEE_CLI_VERSION` or `CLAUDE_CODE_CLI_VERSION` means its default.

## IronBee account and endpoints

| Variable | Default | Mode | Description |
|----------|---------|------|-------------|
| `IRONBEE_API_KEY` | Empty | Both | Your IronBee account API key, from **Settings > Account** in the console. Keep it in a secured repository variable and pass it: `IRONBEE_API_KEY: $IRONBEE_API_KEY` |
| `IRONBEE_CLI_VERSION` | `latest` | Both | IronBee CLI version to install, such as `0.53.0`. Empty means `latest` |
| `IRONBEE_PROJECT` | Empty | Platform | The project the run reports to. Empty derives it from the git remote |
| `IRONBEE_ENVIRONMENT` | Empty | Platform | The project environment the run is against, by name. Selects that environment's variables and secrets on top of the project-wide ones. A new name is created by the first run that uses it. Empty falls back to the step's deployment environment (`BITBUCKET_DEPLOYMENT_ENVIRONMENT`) |
| `IRONBEE_API_URL` | Empty | Platform | IronBee API base URL. Leave empty |
| `IRONBEE_COLLECTOR_URL` | Empty | Both | IronBee collector URL. Leave empty. On IronBee, your app's commands get the resolved URL as `IRONBEE_COLLECTOR_URL`, with the key as `IRONBEE_API_KEY`. See [Your app's own telemetry](#your-apps-own-telemetry) |
| `IRONBEE_CONSOLE_URL` | Empty | Both | Console hostname, without a scheme, used for links in the report. Empty derives it from the collector URL |

## What to verify and what to do about it

| Variable | Default | Mode | Description |
|----------|---------|------|-------------|
| `VERIFICATION_PROMPT` | Empty | Both | Additional instructions for the verification |
| `VERIFICATION_AUTO` | `"true"` | Both | Set `"false"` to verify only in a manual pipeline. Every other pipeline, schedules included, then does nothing. See [Turning automatic verification off](/bitbucket-pipe/guides/running-in-pipelines#turning-automatic-verification-off) |
| `VERIFICATION_APPLY_FIX` | `"true"` | Both | Fix the issues a failing verification reports, in the pipe, and commit the fix. Needs an Anthropic credential; without one, a run on IronBee verifies and reports only. `"false"` verifies and reports in both modes |

The pipe has no `VERIFICATION_COMMAND` variable: Bitbucket Pipelines has no trigger for a pull request comment.

| Variable | Default | Mode | Description |
|----------|---------|------|-------------|
| `BITBUCKET_OAUTH_TOKEN` | Empty | Both | The step's own token, for the report comment, the fix commit and the fix pull request. Pass it as `BITBUCKET_OAUTH_TOKEN: $BITBUCKET_OAUTH_TOKEN`. See [The Bitbucket token](/bitbucket-pipe/get-started/getting-started#the-bitbucket-token) |

## The step around the pipe

The pipe is called from a step of your own, so the step's keys are yours to set:

| Step key | What the pipe needs from it |
|----------|-----------------------------|
| `max-time` | At least what the plan logs: 90 minutes for a run that verifies once, 150 for a run on IronBee that fixes an app in the pipe and verifies it again. Bitbucket's default is 120 |
| `auth.system.scopes` | `read:pullrequest:bitbucket`, `write:pullrequest:bitbucket` and `write:git:bitbucket`, for the step's `BITBUCKET_OAUTH_TOKEN` |
| `artifacts` | `.ironbee/upload/**`, to keep the report and the evidence. See [Evidence](/bitbucket-pipe/advanced/evidence) |
| `caches` | A custom cache for the browser, in local mode. See [Caching](#caching) |
| `services`, `size` | `services: [docker]` and `size: 2x` for an app started with Docker Compose. See [Docker Compose](/bitbucket-pipe/guides/verifying-your-app#docker-compose) |
| `output-variables` | The [outputs](#outputs) to hand to later steps |

### Your app's own telemetry

When the pipe starts your app for a run on IronBee, your app's install, build, start and restart commands run with `IRONBEE_COLLECTOR_URL` (the collector the run reports to) and `IRONBEE_API_KEY` in their environment. An app whose OpenTelemetry exporter reads them ships its traces and logs into the verification run, next to the rest of its evidence. Nothing is written to disk for it.

### Credentials in the pipe

A pipe's variables reach everything it starts. The pipe takes its own variables back out of the environment and gives each step only what it needs: on IronBee, the app the pipe starts gets no Anthropic key, and the agent no Bitbucket token. On your runner, the agent starts your app, so the app inherits the agent's environment, the Anthropic credential and `IRONBEE_API_KEY` included. A variable you pass under another name, such as your app's own secret, reaches every process the pipe starts, your app included.

## Outputs

The pipe writes its outputs to `.ironbee/outputs.env` in the working directory. The step's `after-script` reads them on every run; the step's later script lines run only when the pipe passes. A step that lists them in `output-variables:` also hands them to the steps after it, when the pipe can reach the step's variables file:

```yaml
- step:
    output-variables: [IRONBEE_VERDICT, IRONBEE_JOB_URL]
    script:
      - pipe: docker://ghcr.io/ironbee-ai/ironbee-bitbucket:v1
        variables:
          IRONBEE_API_KEY: $IRONBEE_API_KEY
```

| Variable | Description |
|----------|-------------|
| `IRONBEE_VERDICT` | `pass`, `fail`, `not_applicable` or `unknown` |
| `IRONBEE_MODE` | Where the verification ran: `platform` or `local` |
| `IRONBEE_JOB_ID` | The verification run's id. Platform mode only; after a fix, the re-verification's id |
| `IRONBEE_JOB_URL` | Link to the run in the IronBee Console. Platform mode only, once the run has started |
| `IRONBEE_ARTIFACTS_URL` | The step's page, whose **Artifacts** tab holds the evidence. Local mode only; evidence from a run on IronBee is in the console |
| `IRONBEE_PLATFORM_PUBLISHES` | `true` when IronBee publishes the run on the repository itself: the build status on the commit, and on a pull request its comments and summary comment. The pipe then posts no report comment. `false` otherwise, and always in local mode |

## Caching

In local mode, the pipe installs the Playwright Chromium binaries on every run. A pipe keeps nothing outside the clone, so they live in `.cache/ms-playwright` at the clone's root, and the pipe tells git to ignore that folder. Keep them between runs with a custom cache on the step:

```yaml
definitions:
  caches:
    playwright: .cache/ms-playwright
  steps:
    - step: &ironbee-verify
        caches: [playwright]
```

Platform mode installs no browser.
